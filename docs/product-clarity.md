# Product Clarity

이 문서는 스위트홈이 기능 욕심으로 흐려지지 않도록 제품의 초점을 고정하기 위한 기준입니다.

## One-liner

스위트홈은 사회초년생과 1인가구가 집을 구할 때 후보 지역을 안전, 비용, 교통, 생활 편의성 기준으로 비교하도록 돕는 데이터 기반 주거 의사결정 서비스입니다.

## Target User

초기 타겟은 서울에서 전세 또는 월세를 구하는 사회초년생, 1인가구, 독립 예정자입니다.

이 사용자는 보통 다음 문제를 겪습니다.

- 집을 볼 때 무엇을 중심으로 봐야 하는지 모른다.
- 급하게 집을 구하느라 시야가 좁아진다.
- 안전, 교통, 생활 편의성 같은 조건을 놓친다.
- 여러 사이트를 오가며 비교하다가 판단 기준이 흐려진다.

## Core Problem

사용자는 좋은 집을 추천받고 싶은 것이 아니라, 자신이 고려 중인 지역이나 후보지가 자기 상황에 맞는지 비교하고 싶습니다.

스위트홈이 풀 문제는 다음 두 가지입니다.

1. 후보지를 아는 사용자는 후보 지역 A와 B가 어떤 지표에서 다른지 알고 싶습니다.
2. 후보지를 모르는 사용자는 자신이 중요하게 생각하는 조건을 기준으로 살펴볼 만한 행정동 후보군을 좁히고 싶습니다.

두 경우 모두 최종 판단은 사용자가 합니다. 스위트홈은 특정 지역을 선택하라고 결정하지 않고, 사용자가 선택한 기준으로 데이터를 비교하거나 다시 정렬합니다.

## MVP Scope

초기 MVP는 서울 행정동 단위 지역 비교에 집중합니다.

첫 번째 MVP 화면은 비용 지표를 중심으로 만듭니다. 이미 확보한 서울 전월세 실거래 데이터를 사용해 각 행정동의 전세가/보증금 수준이 서울 평균 대비 높은지 낮은지를 먼저 보여줍니다.

이후 MVP 확장은 두 진입점을 가집니다.

1. 후보지를 아는 경우: 사용자가 직접 선택한 행정동을 비교하고 리포트를 확인합니다.
2. 후보지를 모르는 경우: 사용자가 안전, 편의, 교통, 가격, 인구 같은 조건을 선택하면 서울 행정동 지도와 후보 목록에서 관련 데이터 수치가 상대적으로 많이 관측되는 지역을 보여줍니다.

### Must Have

- 지역 검색 또는 후보 지역 선택
- 후보 지역 2개 비교
- 서울 평균 대비 비용 지표
- 거래량 기반 가격 해석 보조 지표
- 데이터 출처와 기준일 표시
- 종합 해석

### Next Have

- 안전 지표
- 교통 지표
- 생활 편의 지표
- 생활인구/환경 지표
- 사용자 선택 조건 기반 후보지 탐색
- 서울 행정동 지도 기반 heatmap 또는 choropleth

## User-Controlled Candidate Match Policy

스위트홈은 지역을 점수로 평가해 추천하지 않습니다.

사용자가 안전, 편의, 교통, 가격, 인구 같은 조건을 직접 선택하면, 스위트홈은 각 조건과 연결된 데이터 지표를 확인합니다. 그리고 선택 조건과 관련된 수치가 상대적으로 높거나 많이 관측되는 행정동을 후보군으로 보여줍니다.

예시 흐름:

```text
사용자 선택 조건
안전 + 편의
↓
조건별 연결 지표 확인
안심시설수, 유흥시설수, 업종수, 사업체수
↓
관련 지표 수치가 상대적으로 많이 관측되는 행정동 추출
↓
선택 조건 기준 후보군 표시
```

기본 데이터 mart는 행정동별 지표 묶음인 `region_indicator_profile`로 관리합니다. 사용자 조건을 적용한 결과는 저장 테이블보다 API 응답 모델인 `region_candidate_match`에 가깝습니다.

후보군은 절대적인 좋고 나쁨이 아니라, 사용자가 선택한 조건과 관련된 데이터가 상대적으로 많이 관측된 지역의 집합입니다.

사용 가능한 표현:

- "선택한 조건과 관련된 데이터가 많이 관측된 지역"
- "조건 기준 후보군"
- "서울 평균 대비 지표가 높은/낮은 지역"
- "안전 대체 지표가 상대적으로 많은 지역"
- "생활 편의 지표가 상대적으로 높은 지역"

사용하지 않는 표현:

- "추천 지역"
- "최고 지역"
- "가장 살기 좋은 지역"
- "안전한 지역"
- "위험한 지역"
- "점수가 높은 좋은 지역"

### Initial Data Domains

1. 안전
   - 안심시설
   - 유흥시설
   - CCTV 또는 안심시설
2. 비용
   - 월세
   - 전세
   - 실거래 기반 가격
3. 교통
   - 지하철 접근성
   - 버스 접근성
   - 주요 업무지구 이동 시간
4. 생활
   - 병원
   - 약국
   - 편의점
   - 마트
5. 환경
   - 인구밀도
   - 공원

## Not MVP

아래 항목은 좋은 아이디어일 수 있지만 초기 MVP에서는 제외합니다.

- 매물 추천
- 아파트 투자 분석
- 집값 상승 예측
- 학군 중심 서비스
- 신혼부부/육아 특화 서비스
- 소음, 공사, 해충, 분리수거 같은 고난도 민원 데이터
- 모든 지역 전국 확장
- 실시간 교통 최적화
- 사용자 리뷰 커뮤니티
- 매물 크롤링 자동화

## Product Boundary

스위트홈은 다음 문장을 넘지 않습니다.

- "이 집을 사세요"
- "이 지역이 최고입니다"
- "투자 가치가 높습니다"
- "여기가 무조건 안전합니다"

스위트홈이 말할 수 있는 것은 다음입니다.

- "A 지역은 B 지역보다 유흥시설 수가 적습니다."
- "A 지역은 주요 업무지구 이동 시간이 짧습니다."
- "B 지역은 병원과 공원 접근성이 더 좋습니다."
- "선택한 조건과 관련된 지표가 A 지역에서 더 많이 관측됩니다."
- "이 결과는 2026년 기준 확보 데이터에 기반합니다."

## MVP Comparison Report

비교 리포트는 다음 구조를 기본으로 합니다.

1. 후보 지역 요약
2. 사용자의 우선순위 확인
3. 서울 평균 대비 비용 비교
4. 거래량과 데이터 기준일
5. 종합 해석
6. 데이터 출처와 한계

안전, 교통, 생활 편의, 환경 비교는 비용 비교 MVP가 동작한 뒤 순차적으로 추가합니다.

## Interface Decision

첫 번째 MVP는 CLI 리포트로 구현합니다.

선택 이유:

- 프론트엔드나 API 서버보다 데이터 흐름 검증이 먼저입니다.
- `real_estate_price_comparison` mart가 제품 질문에 답하는지 빠르게 확인할 수 있습니다.
- 이후 GraphQL API의 `compareRegions(regionA, regionB, month)` resolver로 확장하기 쉽습니다.

현재 CLI의 역할:

- 사용자가 입력한 행정동명을 `region_id`로 해석합니다.
- 두 후보 지역의 공통 최신 기준월을 선택합니다.
- 서울 평균 대비 가격 수준과 거래량 해석 주의 여부를 출력합니다.
- 추천이나 투자 조언이 아니라 비교 근거만 제공합니다.

## PM Decision Rules

새 기능을 추가하기 전 반드시 아래 질문을 통과해야 합니다.

1. 사회초년생/1인가구의 집 구하기 의사결정에 직접 도움이 되는가?
2. 후보 지역 비교 리포트에 들어갈 수 있는가?
3. 행정동 기준으로 정규화할 수 있는 데이터인가?
4. 지금 가진 데이터 파이프라인으로 재현 가능하게 만들 수 있는가?
5. 추천이나 투자 조언으로 오해될 위험이 없는가?

하나라도 명확하지 않으면 MVP 이후로 미룹니다.
